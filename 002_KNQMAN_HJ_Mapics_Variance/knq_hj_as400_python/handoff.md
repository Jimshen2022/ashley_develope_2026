# KNQ_HJ_AS400 项目交接总结

## 结论

这个主题按代码交付口径已经完成。

已经完成的范围：

- 读取并导出 Excel VBA 宏
- 梳理主要工作表、宏依赖和数据 lineage
- 将原 Excel 报表流程迁移为 Python 项目
- 将 SQL pull 彻底抽成独立 Python connector
- 让 SQL connector 按 VBA `Setup` 页参数规则取值
- 保留手工维护工作表作为 Python 流程输入的一部分
- 提供 snapshot 模式和 live SQL 模式两套运行路径

当前剩余事项不是开发缺口，而是环境验证事项：

- 真实 SQL Server 与 AS400 连接是否在当前机器和当前凭据下可直接执行
- 生产环境调度、日志、异常告警要不要再继续产品化

## 这次成功的关键经验

### 1. 先把 Excel 当成系统，不当成文件

这次不是简单“抄公式”或者“抄几段 SQL”。真正有效的方法，是先把 workbook 当成一个小系统来拆：

- 宏入口是谁触发的
- 每张 sheet 是原始源、过渡层还是最终报表层
- 哪些 sheet 来自 SQL，哪些来自人工维护
- 哪些 VBA 只是展示动作，哪些才是真正业务计算

这个视角很重要。它让迁移目标从“复制 Excel 外观”变成了“重建数据流和控制流”。

### 2. 先建立 lineage，再写 Python

先导出全部 VBA、sheet map、sheet preview、macro dependencies，这一步非常值。它的作用不是文档好看，而是避免后面写 Python 时靠猜。

有了这层分析，后面每个 Python 模块都能回答三个问题：

- 它对应哪段 VBA
- 它消费哪些 sheet 或 SQL 结果
- 它产出的字段最后流向哪里

迁移工作能稳定推进，核心就是 lineage 先行。

### 3. 把“拉数”与“报表计算”彻底拆开

这次最重要的结构性收益，是把 SQL pull 从报表逻辑里独立出来了。

现在项目里已经分成两层：

- connector/source 层负责取数
- pipeline/report 层负责口径和结果计算

这比 VBA 时代更稳，因为后面如果换数据库、改凭据、补缓存、加重试，都不会再碰报表算法本体。

### 4. 参数不能只看“值”，要看“VBA 是怎么拼进去的”

这是本次最容易踩坑、也是最后真正补齐的一点。

同样是 `Setup!C2/C3` 日期参数，VBA 在不同模块里的用法并不一样：

- 有些 SQL 模块把日期自己包进引号
- 有些 SQL 模块直接把单元格原值拼进 `BETWEEN`
- AS400 查询不是用 `C2/C3`，而是用 `Date` 与 `Date - 3` 计算 IBM `CYYMMDD`
- KNQ on-hand 只取目标日，并拼成 `23:59:59`

所以“抽 connector”不能只做成统一日期参数，而要做成“按 VBA 模块语义映射参数”。这一步做到位以后，Python 才算真正遵从原始业务口径。

### 5. VBA SQL 提取器必须适配真实导出格式

另一个关键经验，是不要假设 VBA 导出文本足够规整。

这次导出的 `.bas` 文件在多行 SQL 之间夹了大量空行，而且大量查询是通过：

- `sql_query = "..." & _`
- `sql_query = sql_query & "..."`

这两类方式混合拼接出来的。

如果提取器只支持最理想的连续行格式，就会把查询截断，最后看起来像“模块迁移了”，其实 SQL 只拼出来第一段。

这次补强了解析器之后，才真正把 live SQL connector 做实。

### 6. 保留双模式，是很好的迁移策略

现在项目同时保留了：

- snapshot pipeline
- live SQL pipeline

这是很稳的做法。

原因很简单：

- snapshot 模式适合先做口径复刻和离线比对
- live 模式适合逐步替换 VBA 的实时拉数动作

两条路并存，迁移风险会小很多，也更方便后续验数。

## 建议的下一步

如果进入下一阶段，最值得做的不是继续重写，而是补“运行级能力”：

- 把 live pipeline 在真实库上跑通并留一份基线结果
- 增加每个 source sheet 的行数校验和关键字段空值校验
- 把最终报表输出到标准文件格式，比如 xlsx 或 csv
- 加入配置文件和日志目录，便于交接给其他人维护
- 如果要长期使用，再补调度和失败重跑机制

## 一句话复盘

这次项目能成功，不是因为把 VBA 翻译成了 Python，而是因为先把 Excel 背后的业务数据流、参数语义和查询边界拆清楚了，然后才把它们重建成可维护的 Python 结构。
